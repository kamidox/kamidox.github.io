读懂 mjlab CartPole 教程：从 XML 到 PPO 训练

写在前面¶

最近 Huggingface 的 microduck 爆火，顺腾摸瓜，找到了他们用来进行强化训练的框架 mjlab。

本文通过学习 mjlab 的一个示例教程，来详细了解 mjlab 的一些基本概念，流程，框架。目标是搞清楚，如何用 mjlab 进行强化训练。

mjlab 入门教程文件在这 create_new_task.ipynb，方法就是一步一步看教程，并在 Google 的 colab 里执行训练，然后直接在 notebook 里看到训练后的模型的运行效果。

强化学习的目的，就是要训练一个模型，能够让下图的倒摆锤能够稳定地立在滑块上面。

要复刻此步骤，需要科学上网，并拥有 Google 账户。Google colab 免费提供 GPU 虚拟主机。

不得不感叹，有了 AI 加持，学习效率 N 倍提升，不懂就问，AI 就是个耐心的专家。

以下内容，是看 notebook 过程中，和 AI 交流的过程，让 AI 总结成一篇技术博客。坦白讲，写得比我手搓得好。

mjlab 是什么¶

mjlab 是建立在 MuJoCo 与 mujoco_warp 之上的强化学习仿真框架。MuJoCo 负责刚体动力学，mujoco_warp 提供面向 GPU 的批量仿真能力，而 mjlab 将一个 强化学习任务组织为几个相互协作的 manager：

  • Scene 创建地形、机器人、传感器等场景内容。
  • ActionManager 将策略动作转为 actuator 控制量。
  • ObservationManager 从状态构造策略和 critic 的输入。
  • RewardManager 计算并汇总每一步奖励。
  • EventManager 在 reset、固定间隔等时机改变场景状态。
  • TerminationManager 判断一局是否结束。

这个划分的优点是：任务作者主要描述“观测什么、控制什么、什么行为更好”， 框架负责将这些描述放进重复执行的仿真与 PPO 训练循环。

本例中的装置与训练目标¶

本例的 CartPole 由一辆可沿 $x$ 轴滑动的小车和一根铰接在小车上的杆组成。 在 XML 中，slide 是小车的平移关节，hinge 是杆的转动关节， slide_velocity 是控制小车的速度 actuator。杆没有独立电机：策略只能移动 小车，利用运动产生的动力学效应让杆保持直立。

训练目标是学习一个反馈控制策略：观察杆的角度和角速度、小车的位置和速度， 输出小车速度命令，使杆尽可能接近竖直，同时避免无必要的大幅控制。训练时还会 随机化初始状态、施加外力，让策略不只适应理想条件。

先看全局数据流¶

一次环境交互可概括为：

$$ o_t \xrightarrow{\text{actor}} a_t \xrightarrow{\text{ActionManager}} u_t \xrightarrow{\text{MuJoCo}} s_{t+1} \xrightarrow{\text{reward}} r_t, o_{t+1} $$

其中 $o_t$ 是观测，$a_t$ 是策略的抽象动作，$u_t$ 是写入 actuator 的控制量， $s_{t+1}$ 是物理仿真后的状态。PPO 反复收集 $(o_t, a_t, r_t, o_{t+1}, done)$，并据此更新 actor 和 critic。

在 ManagerBasedRlEnv.step() 中，顺序是：处理动作，按 decimation 执行物理 子步，检查终止，计算奖励，执行 step/interval 事件，为已结束环境 reset，最后 执行一次 forward() 并生成下一帧观测。奖励和终止读取的是物理步后状态；某些 派生量在该时刻可能相对最新积分状态滞后一小步，但对所有环境保持一致。

XML：定义静态模型¶

notebook 先写入 CartPole XML。它定义模型的静态结构与物理参数：body 的层级、 geom 的形状和质量、joint 类型及限制、actuator 的类型及控制范围。简化后关键部分为：

<body name="cart" pos="0 0 0.1">
  <joint name="slide" type="slide" axis="1 0 0" range="-2 2"/>
  <body name="pole" pos="0 0 0.1">
    <joint name="hinge" type="hinge" axis="0 1 0" range="-90 90"/>
  </body>
</body>
<actuator>
  <velocity name="slide_velocity" joint="slide" ctrlrange="-20 20" kv="20"/>
</actuator>

slide 的位置范围是 $[-2,2]$ 米；hinge 的转角范围是 $[-90,90]$ 度。 velocity actuator 接收目标速度命令，其 ctrlrange 限定控制输入为 $[-20,20]$。 XML 不保存某一时刻的运动状态，而是在创建场景时被编译成共享的 MjModel。

SceneCfg：场景和并行环境¶

教程中的场景配置为：

scene_cfg = SceneCfg(
  num_envs=64 if not play else 16,
  extent=1.0,
  entities={"robot": get_cartpole_robot_cfg()},
)
  • num_envs 是并行 world 数。训练使用 64 个彼此独立的 CartPole，以并行收集 经验；play 时设为 16 以减少开销。不过 play 脚本的 --num_envs 会覆盖此值， notebook 传入 4。若仅单步调试或观看一台装置，设为 1 完全合理。
  • entities 将模型以场景名称 robot 加入。后续 action、event、viewer 都通过 这个名称定位该实体。
  • extent=1.0 覆盖 MuJoCo 的 mjModel.stat.extent，主要影响默认相机尺度、 裁剪等显示相关行为。它不是平行环境的间距。环境起点间距应使用 env_spacing，默认值为 2 米。

env.sim.data：每个 world 的运行时状态¶

env.sim.data 是 mjlab 对批量 mujoco_warp.Data 的 PyTorch 访问接口；它不是 原生、单环境的 mujoco.MjData。XML 编译得到共享模型，而 data 保存每一个并行 world 随时间变化的状态。常用数组的第 0 维都是环境维度：

env.sim.data.qpos.shape  # (num_envs, nq)
env.sim.data.qvel.shape  # (num_envs, nv)
env.sim.data.ctrl.shape  # (num_envs, nu)

本例只有两个一维关节和一个 actuator，故关节定义顺序对应为：

字段 CartPole 中的含义
qpos[:, 0] slide 小车位置
qpos[:, 1] hinge 杆角度，单位 rad
qvel[:, 0] 小车速度
qvel[:, 1] 杆角速度，单位 rad/s
ctrl[:, 0] slide_velocity 的速度命令
qfrc_applied[:, 0] 施加在小车滑动自由度的外部广义力

此外，xpos 是各 body 的世界坐标，xquat 是世界朝向四元数，cvel 是空间 速度，qacc 是广义加速度。xpos 和 xquat 等派生量并非直接来自 XML；它们由 MuJoCo 根据 XML 的运动学链以及当前 qpos、qvel 在 forward() 或 step() 中 计算得到。

硬编码 qpos[:, 1] 适合这个极简教程，但复杂模型不应依赖它。env.scene["robot"] 的实体索引保存了其 joint_q_adr、joint_v_adr、ctrl_ids，用于把一个实体的 局部关节、actuator 映射到场景全局 data 数组。

Viewer 与物理步长¶

viewer_cfg = ViewerConfig(
  origin_type=ViewerConfig.OriginType.ASSET_BODY,
  entity_name="robot",
  body_name="pole",
  distance=3.0,
  elevation=10.0,
  azimuth=90.0,
)

ASSET_BODY 表示相机跟随某个刚体；本例目标是 robot 中的 pole body。distance 以米计，elevation 和 azimuth 是以度计的相机仰角和水平环绕角。

MujocoCfg(timestep=0.02, iterations=1)

timestep=0.02 表示物理仿真频率为 $50\,\text{Hz}$。iterations=1 是约束求解器 的迭代次数；它计算快，但复杂接触或约束可能需要更高值以换取稳定性。结合 decimation=1，每个策略动作只推进一个物理步，所以控制周期为：

$$ \Delta t_{control}=0.02\times1=0.02\text{ s}。 $$

Actions：策略怎样控制小车¶

actions = {
  "joint_pos": JointVelocityActionCfg(
    entity_name="robot",
    actuator_names=(".*",),
    scale=20.0,
    use_default_offset=False,
  ),
}

joint_pos 只是字典 key，不决定控制模式。这里真正使用的是 JointVelocityActionCfg，所以它是速度控制；命名为 joint_velocity 或 cart_velocity 会更直观。

entity_name="robot" 指定目标实体。actuator_names=(".*",) 是正则表达式， 匹配该实体的全部 actuator；本例只有 XML 中的 slide_velocity，因此动作维度是 1。 策略不能直接转动 hinge，只能通过移动小车间接让杆回正。

一次 env.step(action) 时，ActionManager 先接收形状为 (num_envs, 1) 的策略 输出，再在物理子步前应用控制。概念上：

target_velocity = policy_action * 20.0
env.sim.data.ctrl[:, 0] = target_velocity

因此 $u_t\approx20a_t$。use_default_offset=False 表示不叠加默认控制偏置。实际 控制输入仍受到 XML 中 ctrlrange="-20 20" 的限制。速度 actuator 可粗略理解为 根据目标速度 $u_t$ 与当前速度 $\dot{x}$ 的差，产生与 $k_v(u_t-\dot{x})$ 相关的驱动力，其中本例 $k_v=20$。

Observations：策略看到了什么¶

本例 actor observation 由四项拼接而成：

angle    = env.sim.data.qpos[:, 1:2] / math.pi
ang_vel  = env.sim.data.qvel[:, 1:2] / 5.0
cart_pos = env.sim.data.qpos[:, 0:1] / 2.0
cart_vel = env.sim.data.qvel[:, 0:1] / 20.0

[:, 1:2] 而非 [:, 1] 的目的，是保留二维的 (num_envs, 1) 张量，方便 concatenate_terms=True 沿特征维拼成 (num_envs, 4)。四项分别是归一化后的杆角、 杆角速度、小车位置、小车速度。

训练时 actor 的 enable_corruption=not play 为真，可启用配置的观测扰动；play 时 关闭，便于观察。critic 使用同一组状态且始终无扰动。本例 actor 与 critic 输入相同， 但更复杂的任务可让 critic 使用额外的特权信息。

Rewards：把训练目标变成数值信号¶

def compute_upright_reward(env):
  return env.sim.data.qpos[:, 1].cos()

def compute_effort_penalty(env):
  return -0.01 * (env.sim.data.ctrl[:, 0] ** 2)

rewards = {
  "upright": RewardTermCfg(func=compute_upright_reward, weight=5.0),
  "effort": RewardTermCfg(func=compute_effort_penalty, weight=1.0),
}

每个 RewardTermCfg 提供一个函数和权重。每次 step() 后，RewardManager 依次调用：

value = term_cfg.func(env, **term_cfg.params)
value = value * term_cfg.weight * step_dt
reward_buf += torch.nan_to_num(value)

函数必须返回形状 (num_envs,) 的张量：不是一个总分，而是为每一个并行 CartPole 算一个分数。各项同时累积到总奖励 env.reward_buf 和各自的 episode 统计中。

对于杆角 $\theta$、控制量 $u$：

$$ r_{raw}=5\cos(\theta)-0.01u^2。 $$

杆直立时 $\cos(0)=1$，得到最大的 upright 奖励；偏至 $90^\circ$ 时接近 0。 effort 为二次惩罚，促使策略在能平衡时减少大幅速度命令。例如 $u=10$ 时原始 惩罚为 $-1$。

框架默认 scale_rewards_by_dt=True。本例 step_dt=0.02 秒，最终每控制步进入 buffer 的奖励是：

$$ r_{step}=\left(5\cos(\theta)-0.01u^2\right)\times0.02。 $$

这样调整物理频率后，固定真实时间内的累计奖励量级不会仅因步数改变而失真。

Events：改变初始条件与训练难度¶

event 不直接提供奖励，而是在指定时机主动写入状态或物理参数。它常用于随机初始 状态、外力扰动、domain randomization 和课程学习。本例有两个事件。

reset_robot_joints¶

"reset_robot_joints": EventTermCfg(
  func=mdp.reset_joints_by_offset,
  mode="reset",
  params={
    "asset_cfg": SceneEntityCfg("robot"),
    "position_range": (-0.1, 0.1),
    "velocity_range": (-0.1, 0.1),
  },
)

mode="reset" 表示每次某个环境开始新 episode 时运行。它为 robot 所有相关关节 添加随机位置和速度偏移。本例中小车位置、杆角、小车速度、杆角速度都会在默认值附近 随机取值，大致范围为 $[-0.1,0.1]$（角度单位为 rad）。这样策略必须处理略偏、略动 的起点，不能只记住完全静止、严格竖直的初态。

该事件在训练和 play 都存在。因此 play 中每次倾倒后，新一局仍有轻微随机初态；若 需要完全可复现的演示，可仅在训练模式加入它，或将范围设为 (0.0, 0.0)。

random_push¶

events["random_push"] = EventTermCfg(
  func=random_push_cart,
  mode="interval",
  interval_range_s=(1.0, 2.0),
  params={"force_range": (-20.0, 20.0)},
)

它只在 not play 时注册。mode="interval" 表示每个环境在运行中按随机的 1 到 2 秒间隔触发。random_push_cart 将随机力写入：

env.sim.data.qfrc_applied[env_ids, 0] = random_forces

索引 0 对应 slide 自由度，因此这是沿小车滑轨方向的推力，范围是 $[-20,20]$。 它迫使策略学习在被推向任一方向后恢复平衡。play 时关闭该扰动，便于稳定展示已学到 的行为。

Terminations：何时结束一局¶

terminations = {
  "timeout": TerminationTermCfg(func=mdp.time_out, time_out=True),
  "tipped": TerminationTermCfg(func=check_pole_tipped, time_out=False),
}
  • timeout 是正常时间截断。训练时 episode_length_s=10.0，按 50 Hz 约为 500 个 控制步；time_out=True 让算法知道这不是任务失败。
  • tipped 在 $|\theta|>30^\circ$ 时终止，是真实失败。
  • play 时 episode_length_s=int(1e9)，可视为没有超时限制，但杆倾倒仍会终止并 reset。

RslRlOnPolicyRunnerCfg：如何训练 PPO¶

教程的 cartpole_ppo_runner_cfg() 创建 RslRlOnPolicyRunnerCfg。on-policy 意味着 每轮先用当前策略采样一批新轨迹，再用这批数据更新，PPO 不会长期复用旧策略的数据。

Actor 与 Critic 网络¶

actor=RslRlModelCfg(
  hidden_dims=(256, 128, 64),
  activation="elu",
  obs_normalization=True,
  distribution_cfg={
    "class_name": "GaussianDistribution",
    "init_std": 1.0,
    "std_type": "scalar",
  },
)

actor 是三层 MLP，可近似看作 $4\rightarrow256\rightarrow128\rightarrow64\rightarrow1$。 elu 是隐藏层激活函数；obs_normalization=True 会对输入维度做运行时标准化。

GaussianDistribution 表示 actor 输出动作均值，并从高斯策略中采样：

$$ a_t\sim\mathcal{N}(\mu_\theta(o_t),\sigma^2)。 $$

init_std=1.0 为初始探索设定标准差；std_type="scalar" 表示所有动作共享一个 可学习标准差。本例只有一个动作维度，因而尤其直接。

critic 的 hidden_dims、activation 和 obs_normalization 相同，但没有 distribution_cfg，因为它不采样动作，而是确定性地输出价值估计：

$$ V_\phi(o_t)\approx\mathbb{E}\left[\sum_{k=0}^{\infty}\gamma^kr_{t+k}\right]。 $$

PPO 超参数¶

  • value_loss_coef=1.0：critic 价值误差在总 loss 中的权重。
  • use_clipped_value_loss=True：限制 critic 的单次价值更新幅度。
  • clip_param=0.2：PPO 策略概率比的核心裁剪范围，约束新旧策略不要在一次更新中相差 过远。
  • entropy_coef=0.01：鼓励策略保持一定随机性以探索；过大则会妨碍收敛。
  • num_learning_epochs=5：每一批新轨迹用于 5 轮梯度训练。
  • num_mini_batches=4：每轮将采样数据切为 4 个 mini-batch。训练配置下的 batch 大小是 $64\times24/4=384$ 条转移。
  • learning_rate=1.0e-3：Adam 的初始学习率。
  • schedule="adaptive" 与 desired_kl=0.01：根据新旧策略的 KL 散度自适应调整 学习率；KL 过高通常降低学习率，过低可提高学习率。
  • gamma=0.99：未来奖励的折扣因子。
  • lam=0.95：GAE 参数，在回报估计的偏差和方差之间折中。
  • max_grad_norm=1.0：裁剪过大的梯度，防止不稳定更新。

采样、迭代、保存¶

experiment_name="cartpole"
save_interval=50
num_steps_per_env=24
max_iterations=5_000
  • experiment_name="cartpole"：日志与模型归入 logs/rsl_rl/cartpole/。
  • num_steps_per_env=24：每次更新前，每个环境采 24 步。训练时一轮共收集 $64\times24=1536$ 条转移，每个环境贡献 $24\times0.02=0.48$ 秒仿真轨迹。
  • max_iterations=5_000：最多执行 5,000 轮“采样 + PPO 更新”，理论交互步数约为 $5{,}000\times64\times24=7{,}680{,}000$。
  • save_interval=50：每 50 轮保存 checkpoint。

notebook 实际训练命令传入 --agent.max-iterations 201 和 --agent.save-interval 20，命令行参数会覆盖配置中的这两个值。因此教程运行时最多 训练 201 轮，并每 20 轮保存一次；网络结构和其余 PPO 参数保持不变。

建议的阅读顺序¶

阅读 notebook 时，可按以下链路核对每个配置的作用：

  1. 从 XML 的 slide、hinge、slide_velocity 确认装置有哪些状态和执行器。
  2. 在 SceneCfg 中确认并行环境数和实体名 robot。
  3. 在 observations 中确认哪些 qpos、qvel 会给 actor 与 critic。
  4. 在 actions 中确认策略唯一输出如何变成 ctrl[:, 0]。
  5. 在 rewards 中检查什么状态得到正奖励、什么控制会被惩罚。
  6. 在 events 中检查初始随机化和中途扰动如何增强鲁棒性。
  7. 在 terminations 中确认失败和超时条件。
  8. 最后阅读 PPO 配置，理解一轮采集多少数据、如何分批更新以及何时保存。

沿这条链路看，CartPole 任务的本质很清楚：策略读取状态，控制小车，物理引擎更新杆的 运动，奖励评价“直立且省力”，PPO 再用大量并行轨迹不断改进策略。
